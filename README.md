# Умный кредитный кабинет предпринимателя

Прототип цифрового кредитного конвейера для малого и микробизнеса (кейс Alfa Hack 2026). Клиентский путь и внутренняя обработка заявки объединены в один процесс: клиент выбирает продукт и подаёт заявку, банк проверяет её, оценивает риск и принимает решение, статус виден обеим сторонам.

> **Статус:** в работе. Go API реализует вход, сессии и обновление коэффициента долговой нагрузки через Python worker. В worker есть заглушки проверки заявки, парсинга документов и оценки критического риска. REST API заявок и веб-интерфейс ещё не реализованы.

## Возможности (цель MVP)

- Вход клиентов и сотрудников по телефону или почте (на выбор) и паролю, оба с 2FA-заглушкой. *Реализовано.*
- После входа клиента коэффициент долговой нагрузки (долг / капитал) обновляется из кредитной истории, если он старше 12 часов. *Реализовано.*
- Кабинет клиента: действующие кредиты, долговая нагрузка, выбор продукта, калькулятор.
- Заявка: автозаполнение по ИНН, документы и согласия на БКИ, проверка полноты полей.
- Обработка заявки банком: проверки через моки, скоринг, кредитное решение, ручная проверка андеррайтером.
- Результат: одобрение, отказ, встречное предложение или запрос данных; подписание и выдача имитируются.

## Требования к окружению

- Docker с Docker Compose v2 — единственное требование для запуска.
- Для разработки без Docker: Go 1.26 и Python 3.13.

## Запуск

```bash
docker compose up --build
```

Поднимутся Go API, Python worker, PostgreSQL 17 и Redis 7.2, миграции применятся автоматически. Приложение откроется на http://localhost:8080, проверка работоспособности — http://localhost:8080/healthz.

Без Docker нужны запущенные PostgreSQL и Redis с применёнными миграциями:

```bash
DATABASE_URL="postgres://credit:credit@localhost:5432/credit?sslmode=disable" go run ./cmd/api
```

```bash
python3 -m venv .venv
.venv/bin/pip install -r worker/requirements.txt
REDIS_ADDR=localhost:6379 .venv/bin/python -m worker.main
```

## Миграции

При `docker compose up` их применяет сервис `migrate`, приложение стартует после его успешного завершения. Вручную:

```bash
goose -dir migrations postgres "$DATABASE_URL" up
```

В миграциях две записи: `00001_init.sql` создаёт схему целиком, `00002_seed_demo_data.sql` загружает демо-данные. Откат последней миграции — `down`, состояние — `status`. Если база уже создавалась прежними версиями миграций, её нужно пересоздать (`docker compose down -v`), иначе goose сочтёт старые версии применёнными. Установка: `go install github.com/pressly/goose/v3/cmd/goose@latest`.

## Структура проекта

| Путь | Назначение |
|---|---|
| `cmd/api` | Точка входа HTTP-сервиса |
| `worker/` | Отдельный Python-сервис: маршрутизатор, проверка данных, парсинг документов и риск |
| `internal/app` | Сборка и жизненный цикл приложения |
| `internal/config` | Конфигурация из переменных окружения |
| `internal/handler` | HTTP-обработчики и маршрутизация, к Redis и базе не обращаются |
| `internal/middleware` | Аутентификация по токену и проверка роли |
| `internal/service` | Бизнес-логика: вход с 2FA, обновление коэффициента долговой нагрузки |
| `internal/repository` | Доступ к PostgreSQL (компании, пользователи) и к Redis (сессии, коды 2FA, счётчики попыток) |
| `internal/domain` | Доменные типы и ошибки |
| `internal/queue` | Go-клиент для обмена с Python worker через Redis |
| `internal/catalog` | Каталог 14 кредитных продуктов: сроки, правила допуска, группы полей формы, обязательные документы (`products.yaml`) |
| `migrations` | SQL-миграции в формате [goose](https://github.com/pressly/goose) (`NNNNN_name.sql`) |
| `web` | Статика веб-интерфейса |
| `docs` | Схемы, OpenAPI, тестовые сценарии |

## Сценарий проверки

Полный сценарий появится вместе с заявками. Сейчас проверяются запуск, вход и обновление коэффициента (запросы готовы в [docs/requests.http](docs/requests.http)):

1. `docker compose up --build`
2. `GET http://localhost:8080/healthz` возвращает `{"status":"ok"}`.
3. Вход клиента `+79990000002` (или `client2@example.test`): `POST /api/v1/auth/login` с полем `login`, затем `POST /api/v1/auth/verify` с кодом `000000` возвращает токен и `redirect: /personalAccount`.
4. `POST /api/v1/me/bootstrap` с этим токеном возвращает коэффициент: данных у компании не было, они пришли от воркера.
5. Вход сотрудника `underwriter@example.test` возвращает `redirect: /employee`; тот же токен на `/me/bootstrap` даёт 403.
6. Три неверных пароля подряд блокируют вход на 15 минут (429).

Все реализованные обработчики проверяет скрипт (нужен запущенный стек, ответы сверяются автоматически):

```bash
bash scripts/smoke.sh
```

Адрес можно передать аргументом, например `bash scripts/smoke.sh http://localhost:8080`.

## Допущения и упрощения

- Кредитную историю отдаёт Python-верификатор с синтетическими данными. Парсер и проверка риска пока возвращают явно помеченные ответы-заглушки.
- Вторая ступень аутентификации — заглушка с фиксированным кодом; SMS и почта не используются.
- Если коэффициент устарел, а воркер не отвечает, используются прежние значения. Если данных не было вовсе, клиент получает 503 и повторяет запрос.
- Подписание документов и выдача средств имитируются без реальных операций.
- Все данные синтетические. Платных API и закрытых лицензий решение не использует.
