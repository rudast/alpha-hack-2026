# Умный кредитный кабинет предпринимателя

Прототип цифрового кредитного конвейера для малого и микробизнеса (кейс Alfa Hack 2026). Клиентский путь и внутренняя обработка заявки объединены в один процесс: клиент выбирает продукт и подаёт заявку, банк проверяет её, оценивает риск и принимает решение, статус виден обеим сторонам.

> **Статус:** в работе. Реализованы веб-интерфейс, вход с двухфакторной заглушкой, каталог, черновики и отправка заявок, обновление показателей компании и Python worker для проверки заявок и чтения документов. Worker возвращает результаты через Redis; статусы и решения в PostgreSQL записывает Go API. Ручное решение сотрудника и полноценная проверка внешними источниками ещё в разработке.

## Возможности (цель MVP)

- Вход клиентов и сотрудников по телефону или почте (на выбор) и паролю, оба с 2FA-заглушкой. *Реализовано.*
- После входа клиента коэффициент долговой нагрузки (долг / капитал) обновляется из кредитной истории, если он старше 12 часов. *Реализовано.*
- Кабинет клиента: действующие кредиты, долговая нагрузка, выбор продукта, калькулятор.
- Заявка: черновик с автосохранением, проверка полноты полей по каталогу продуктов, отправка. *Реализовано.* Автозаполнение по ИНН, документы и согласия на БКИ ещё впереди.
- Обработка заявки банком: задачу воркеру скоринга отправляет сборщик, результаты воркера API принимает и применяет к заявке. *Реализовано со стороны API.* Проверки через моки, скоринг, кредитное решение и ручная проверка андеррайтером остаются за воркером и сотрудником.
- Результат: одобрение, отказ, встречное предложение или запрос данных; подписание и выдача имитируются.

## Требования к окружению

- Docker с Docker Compose v2 — единственное требование для запуска.
- Для разработки без Docker: Go 1.26.

## Запуск

```bash
docker compose up --build
```

Поднимутся Go API, Python worker, сервис ассистента, PostgreSQL 17 и Redis 7.2; миграции применятся автоматически. Сайт откроется на http://localhost:8080, документация API — на http://localhost:8080/docs, проверка работоспособности — на http://localhost:8080/healthz.

Без Docker нужны запущенные PostgreSQL и Redis с применёнными миграциями:

```bash
DATABASE_URL="postgres://credit:credit@localhost:5432/credit?sslmode=disable" go run ./cmd/api
```

```bash
python3 -m pip install -r worker/requirements.txt
REDIS_ADDR=localhost:6379 WORKER_PROTOCOL=backend python3 -m worker.main
```

## Миграции

При `docker compose up` их применяет сервис `migrate`, приложение стартует после его успешного завершения. Вручную:

```bash
goose -dir migrations postgres "$DATABASE_URL" up
```

`00001_init.sql` создаёт основную схему, `00002_seed_demo_data.sql` загружает демо-данные, `00003_application_work.sql` и `00004_document_text_status.sql` добавляют хранение документов и заданий worker. Откат последней миграции — `down`, состояние — `status`. Существующие данные сохраняйте при обновлении; не удаляйте том PostgreSQL без отдельной необходимости. Установка: `go install github.com/pressly/goose/v3/cmd/goose@latest`.

## Сценарий проверки

Проверяются запуск, вход, обновление коэффициента и заявки клиента (запросы готовы в [docs/requests.http](docs/requests.http)). После отправки Python worker обрабатывает заявку и передаёт результат Go API через Redis; при недостающих данных заявка может перейти в `INFO_REQUESTED`:

1. `docker compose up --build`
2. `GET http://localhost:8080/healthz` возвращает `{"status":"ok"}`.
3. Вход клиента `+79990000002` (или `client2@example.test`): `POST /api/v1/auth/login` с полем `login`, затем `POST /api/v1/auth/verify` с кодом `000000` возвращает токен и `redirect: /personalAccount`.
4. `POST /api/v1/me/bootstrap` с этим токеном возвращает коэффициент: данных у компании не было, они пришли от воркера.
5. Вход сотрудника `underwriter@example.test` возвращает `redirect: /employee`; тот же токен на `/me/bootstrap` даёт 403.
6. Три неверных пароля подряд блокируют вход на 15 минут (429).
7. Заявка: `POST /api/v1/applications` создаёт черновик, `PATCH /api/v1/applications/{id}` сохраняет изменения (нужны `version` и заголовок `Idempotency-Key`), `POST /api/v1/applications/{id}/submit` отправляет заявку (первый статус `SUBMITTED`).

Все реализованные обработчики проверяет скрипт (нужен запущенный стек, ответы сверяются автоматически):

```bash
bash scripts/smoke.sh
```

Адрес можно передать аргументом, например `bash scripts/smoke.sh http://localhost:8080`.

Кредиты в банке это заявки в статусах `ACTIVE`, `OVERDUE` и `CLOSED` с полной историей переходов и решением скоринга (отдельной таблицы кредитов нет). Они отдаются в `GET /api/v1/loans` с графиком платежей, который считается на лету; в `GET /api/v1/applications` их нет. Даты действующих кредитов отсчитываются от дня создания базы, поэтому ближайший платёж всегда в будущем (у просроченного — прошёл). Долги в других банках (`credit_history.other_banks`) вместе с остатками наших кредитов дают `total_debt`.

## Допущения и упрощения

- Кредитную историю отдаёт воркер-мок с синтетическими данными; остальные внешние сервисы (ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес») будут воспроизведены так же.
- Вторая ступень аутентификации — заглушка с фиксированным кодом; SMS и почта не используются.
- Если коэффициент устарел, а воркер не отвечает или вернул ошибку, используются прежние значения. Если данных не было вовсе, клиент получает 503 и повторяет запрос.
- Подписание документов и выдача средств имитируются без реальных операций.
- Все данные синтетические. Платных API и закрытых лицензий решение не использует.
