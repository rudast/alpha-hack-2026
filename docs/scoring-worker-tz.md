# ТЗ: воркер скоринга

Техническое задание для разработчика воркера скоринга (Python) в проекте «Умный кредитный кабинет предпринимателя». Воркер получает отправленные клиентами заявки, собирает данные, считает балл и принимает автоматическое решение. Связь с API (Go) идёт только через Redis.

Связанные документы:
- [scoring.md](scoring.md) — модель скоринга: факторы, веса, бины, стоп-факторы, пороги, встречное предложение, ставка, формат `decision`;
- [worker-protocol.md](worker-protocol.md) — протокол обмена через Redis (этот документ на него опирается; при расхождении верен протокол);
- [state-diagram.md](state-diagram.md) — статусы заявки.

## 1. Границы ответственности

| Воркер делает | Воркер не делает |
|---|---|
| Читает задачи из Redis stream `applications:submitted` | Не подключается к PostgreSQL: статусы и решение в базу пишет API |
| Сообщает о каждом шаге в stream `applications:results` | Не выносит отказ (`REJECTED`): автоматического отказа нет |
| Запрашивает внешние данные: БКИ, ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес» (моки) | Не участвует в ручной проверке: после `MANUAL_REVIEW` заявкой занимается сотрудник через API |
| Разбирает загруженные PDF, если продукту нужен оборот | Не работает с клиентом напрямую (подписание, встречное предложение решает клиент через API) |
| Считает балл и решение по [scoring.md](scoring.md) | |

## 2. Окружение

- Запуск отдельным сервисом в `docker-compose.yml` рядом с `app`, `redis`, `db`.
- `REDIS_ADDR` — адрес Redis (в compose `redis:6379`). Авторизации и TLS нет.
- Конфигурация модели (`scoring.yaml`, раздел 16 [scoring.md](scoring.md)) — в коде воркера.
- PDF, JPG и PNG клиентов лежат в Docker-томе `documents` по схеме `<id заявки>/<вид>/<имя файла>`. Том подключается к воркеру **только на чтение**, например `documents:/data/documents:ro`; путь к файлу — `/data/documents/` + `path` из задачи. Разобранные данные в базу не пишутся: воркер читает файлы сам при каждой обработке.

## 3. Входная очередь: `applications:submitted`

### Группа потребителей
Группу создаёт воркер при старте (API её не создаёт):
```
XGROUP CREATE applications:submitted scoring-workers 0 MKSTREAM
```
- Ошибку `BUSYGROUP` (группа уже есть) игнорировать.
- Позиция `0`, а не `$`: иначе задачи, отправленные до первого запуска воркера, будут пропущены.
- Имя группы `scoring-workers` предлагается; если выбрано другое, сообщить команде backend.

### Чтение
```
XREADGROUP GROUP scoring-workers <имя-экземпляра> COUNT 10 BLOCK 5000 STREAMS applications:submitted >
```
Несколько экземпляров воркера с разными именами делят задачи между собой.

### Поля задачи
Все значения в Redis приходят строками; JSON-поля нужно разобрать.

| Поле | Тип | Описание |
|---|---|---|
| `application_id` | строка (UUID) | Идентификатор заявки; ключ идемпотентности |
| `inn` | строка | ИНН: 10 цифр у ООО, 12 у ИП |
| `product_id` | строка | Продукт из каталога (`internal/catalog/products.yaml`) |
| `amount` | целое | Сумма, рубли |
| `term_months` | целое | Срок, месяцы |
| `form` | JSON-строка | Форма заявки блоками `группа.поле` (поля продукта описаны в каталоге) |
| `documents` | JSON-строка | Загруженные документы: `[{"kind", "name", "path"}]`, `kind` — вид из каталога (`account_statement`, `financial_statements`…), `path` — путь внутри тома |
| `company` | JSON-строка | `org_type`, `okved`, `registration_date` (`YYYY-MM-DD`, может отсутствовать), `registry`, `credit_history`, `financials` — то, что уже известно о компании; пустые данные приходят как `{}` |
| `debt`, `equity` | целое | Общий долг (наши кредиты плюс другие банки, считает API) и капитал, рубли; полей нет, если показатели не получены |
| `debt_to_equity` | число строкой | Долг / капитал; поля нет, если не определён |

Пример и подробности — [worker-protocol.md](worker-protocol.md), раздел «Задачи по заявкам».

## 4. Порядок обработки заявки

1. **Сразу** после получения задачи отправить `SUBMITTED → DATA_CHECK`. Это сигнал API, что заявка взята в работу; пока заявка в `SUBMITTED`, API каждые 2–3 минуты отправляет задачу повторно.
2. **Собрать данные** (шаг `DATA_CHECK`):
   - из задачи: форма, показатели компании, блок `company`;
   - из внешних сервисов: БКИ (просрочки, запросы за 90 дней, длина истории — раздел 14 [scoring.md](scoring.md)), ЕГРЮЛ/ЕГРИП и «Прозрачный бизнес» (красные и жёлтые флаги);
   - из PDF — только для продуктов, где считается оборот:

     | Продукт | Что извлечь | Документ (`kind`) |
     |---|---|---|
     | `overdraft`, `credit_line` | средний месячный оборот за 6–12 мес; для `credit_line` ещё помесячные обороты | `account_statement` |
     | `working_capital` | годовой оборот / 12 | `financial_statements` |
     | `loan_up_to_1m` | месячный оборот | `account_statement` |
     | `marketplace_seller` | месячный оборот площадки | `marketplace_sales_report` |
3. **Если не хватает данных или документа** — отправить `DATA_CHECK → INFO_REQUESTED` и закончить обработку. Текст для клиента («загрузите выписку по расчётному счёту за 12 месяцев») передать в поле `info_request` и продублировать в `comment`: пока API не сохраняет `info_request`, клиент увидит текст только в истории заявки.
4. **Иначе** отправить `DATA_CHECK → SCORING` и посчитать балл, стоп-факторы, ограничители, решение, ставку и встречное предложение по [scoring.md](scoring.md) (разделы 4–10).
5. **Отправить итог** одним из переходов:
   - `SCORING → APPROVED` — автоматическое одобрение;
   - `SCORING → COUNTER_OFFER` — встречное предложение (условия в `decision.offer`);
   - `SCORING → MANUAL_REVIEW` — нужна ручная проверка (стоп-фактор, низкий балл, сумма выше лимита автоодобрения).

   В сообщении передать `decision` в формате раздела 11 [scoring.md](scoring.md), включая `factors[].value` (исходные значения признаков нужны сотруднику на ручной проверке).
6. **Подтвердить задачу** (`XACK applications:submitted scoring-workers <id>`) только после того, как отправлен последний результат по ней.

## 5. Выходная очередь: `applications:results`

```
XADD applications:results * event_id <uuid> application_id <uuid> from <статус> to <статус> [decision <json>] [comment <текст>] [info_request <текст>]
```

| Поле | Обязательно | Описание |
|---|---|---|
| `application_id` | да | Тот же, что в задаче |
| `from` | да | Статус, в котором заявка находится сейчас |
| `to` | да | Новый статус |
| `event_id` | нет | Уникальный идентификатор сообщения (UUID); попадает в журнал API |
| `decision` | нет | JSON-объект решения; сохраняется в заявке как есть |
| `comment` | нет | Пояснение; добавляется к записи в истории заявки |
| `info_request` | нет | Вопрос клиенту при `INFO_REQUESTED` (API пока не сохраняет) |

Пример итогового сообщения:
```
XADD applications:results * event_id 9c3e... application_id 8c1f... from SCORING to APPROVED \
  decision '{"model_version":"scoring-1","product_id":"working_capital","class":"U","score":85.0,"outcome":"APPROVED","rate":21.25,...}'
```

## 6. Разрешённые переходы

API принимает от воркера только эти переходы; любой другой отклоняется (заявка не меняется, причина пишется в журнал API, воркер ответа не получает).

| Переход | Когда |
|---|---|
| `SUBMITTED → DATA_CHECK` | взял заявку в работу |
| `DATA_CHECK → INFO_REQUESTED` | не хватает данных |
| `DATA_CHECK → SCORING` | данных достаточно |
| `SCORING → APPROVED` | автоодобрение |
| `SCORING → COUNTER_OFFER` | встречное предложение |
| `SCORING → MANUAL_REVIEW` | ручная проверка |

Запрещено: `REJECTED` в любом виде; любые переходы из `MANUAL_REVIEW` (решает сотрудник); `INFO_REQUESTED → DATA_CHECK` (делает API, когда клиент дополнил данные).

## 7. Надёжность

- **Одна заявка может прийти несколько раз.** API повторяет задачу, пока заявка в `SUBMITTED` (каждые 2–3 минуты), а в будущем — и если она долго стоит в `DATA_CHECK` или `SCORING`. Воркер должен быть идемпотентным по `application_id`.
- **Всегда отправлять цепочку целиком, с `SUBMITTED → DATA_CHECK`.** API применяет переход, только если заявка сейчас в статусе `from`; уже пройденные шаги он молча пропускает. Поэтому при повторной задаче достаточно пройти цепочку заново: лишние сообщения безвредны.
- **Порядок.** Результаты одной заявки отправлять строго по порядку (следующий `from` равен предыдущему `to`), не параллельно.
- **Падение воркера.** Задачи, прочитанные, но не подтверждённые, остаются в группе. Их нужно периодически забирать и обрабатывать заново:
  ```
  XAUTOCLAIM applications:submitted scoring-workers <имя-экземпляра> 60000 0-0 COUNT 10
  ```
  (раз в 10–30 секунд; порог простоя больше, чем обычная обработка одной заявки).
- **Временные сбои внешних сервисов** воркер обрабатывает сам (повторы, таймауты). Если заявку посчитать не удаётся, допустимые исходы — только переходы из раздела 6; например, `SCORING → MANUAL_REVIEW` с причиной в `comment`.
- **Данные сообщения:** `decision` — JSON-объект (не массив, не строка); деньги — целые рубли; в тексте не должно быть нулевых символов (`\u0000`): PostgreSQL их не принимает.

## 8. Как проверить

1. `docker compose up --build` поднимает API, Redis, PostgreSQL с демо-данными.
2. Войти клиентом, создать, заполнить и отправить заявку — готовые запросы в [requests.http](requests.http) (тестовые учётные записи в README).
3. Задача появится в `applications:submitted` сразу после отправки:
   ```
   docker compose exec redis redis-cli XREVRANGE applications:submitted + - COUNT 1
   ```
4. После обработки воркером `GET /api/v1/applications/{id}` показывает итоговый статус, `decision` и историю переходов (`by: worker`).

**Критерии приёмки:**
- задача, отправленная до запуска воркера, обрабатывается после его запуска;
- по заявке с полными данными приходит цепочка `DATA_CHECK → SCORING → итог` с `decision` по разделу 11 [scoring.md](scoring.md);
- повторная задача по той же заявке не меняет результат и не ломает обработку;
- при остановке воркера посреди обработки задача после перезапуска доводится до конца;
- результаты сценариев S1–S17 из [scoring.md](scoring.md) совпадают с расчётом (юнит-тесты воркера).
