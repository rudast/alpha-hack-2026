# Задачи

Список того, что ещё не сделано или ждёт решения. Состояние на момент написания: реализованы вход, коэффициент долговой нагрузки, каталог продуктов, заявки клиента с идемпотентностью, сборщик застрявших заявок и приём результатов воркера скоринга (см. [architecture.md](architecture.md)).

Задачи из раздела «Ждут решения» (кроме выполненных) не начаты намеренно: каждая меняет уже работающее поведение или договорённости, поэтому сначала нужно согласие команды.

## Ждут решения

### 1. Отправлять задачу воркеру сразу при отправке заявки — сделано
- `ApplicationService.Submit` после сохранения заявки сразу публикует задачу в `applications:submitted` и ставит `enqueued_at` ([service/application.go](../internal/service/application.go), метод `dispatch`; сборка задачи общая с сборщиком, `newApplicationTask` в [sweeper.go](../internal/service/sweeper.go)).
- Сбой публикации или метки не отменяет отправку: клиент получает 200, ошибка пишется в лог, задачу позже отправит сборщик.
- Проверено: юнит-тесты (`TestApplicationSubmit_*`) и запущенный стек, см. сценарии C1 и C6 в [test-scenarios.md](test-scenarios.md).

### 2. Защита от результатов не по порядку при нескольких экземплярах API
- **Сейчас:** группа `api` делит сообщения между экземплярами. Если два результата одной заявки (`DATA_CHECK`, затем `SCORING`) попадут разным экземплярам, второй может прийти раньше и будет отклонён как «устаревший» (`status != from`). Переход потеряется.
- **Варианты:** (а) оставить как есть: пока экземпляр один, проблемы нет; (б) в обработчике при `ErrStatusMismatch` не подтверждать сообщение, а повторять позже (ограничив число попыток); (в) требовать от воркера слать результаты одной заявки в один шард (по хэшу `application_id`).
- **Предлагается:** (а) для хакатона, (б) если планируется несколько экземпляров API.
- **Где:** [service/results.go](../internal/service/results.go), [queue/results.go](../internal/queue/results.go).

### 3. Версия в `submit`
- **Сейчас:** `PATCH` требует `version`, `submit` нет. Двойную отправку закрывает условие `status = 'DRAFT'`, но отправка не проверяет, что клиент видел последнюю версию формы (например, другая вкладка успела изменить данные).
- **Что сделать:** принимать `version` в теле `submit`; при несовпадении 409.
- **Цена:** меняется контракт для фронта.
- **Где:** [handler/application.go](../internal/handler/application.go), [repository/application.go](../internal/repository/application.go) (`Submit`), [openapi.yaml](openapi.yaml).

### 4. Постраничный `GET /applications`
- **Сейчас:** список отдаёт все заявки компании без ограничения.
- **Что сделать:** `limit` и курсор (`created_at`, `id`); индекс `(company_inn, created_at DESC)` уже есть.
- **Нужно ли:** при десятках заявок на компанию нет; пригодится, если появятся тестовые компании с сотнями.

### 7. Удаление брошенных черновиков
- Черновики старше 30 дней удаляются. Решение принято, код не написан.
- **Как:** фоновая задача рядом со сборщиком, `DELETE FROM applications WHERE status = 'DRAFT' AND updated_at < now() - interval '30 days'` (по `updated_at`, а не `created_at`, чтобы не удалять заявки, с которыми работают).
- **Вопрос:** удалять физически или помечать; сейчас физически, так как документов к черновикам нет.

### 8. Загрузка документов — сделано
- Файлы хранятся только в Docker-томе `documents` по схеме `<id заявки>/<вид>/<имя файла>`; в базе о документах ничего нет (колонка `applications.documents` убрана). `POST /applications/{id}/documents` (multipart, PDF/JPG/PNG до 10 МБ) и `DELETE .../documents/{docId}`, только для черновика; список в `GET /applications/{id}`; пути к файлам — в задаче воркеру.
- **Осталось:** подключить том к воркеру скоринга (только чтение). Проверку обязательных документов продукта при `submit` (`catalog.RequiredDocuments`) не включали: в базовом наборе есть `bki_consent`, а согласие на БКИ фронт передаёт галочкой в `form.consents`; нужно решить, какие документы действительно обязательны.
### 9. Запрос данных у клиента (`INFO_REQUESTED`)
- **Сделано:** запрос хранится в `applications.info_request` (от сотрудника и от воркера: текст из поля `info_request` сообщения, а если его нет, комментарий) и виден клиенту; клиент догружает документы и вызывает `POST /applications/{id}/resume`, заявка возвращается туда, откуда запросили (от сотрудника — в пул, от воркера — в `DATA_CHECK` с повторной задачей).
- Показатели компании воркеру нужны всегда, поэтому `submit` сам получает их, если их ещё не запрашивали (иначе воркер просил бы у клиента долг и капитал, которых клиент дать не может).

### 30. Проверка воркера скоринга в интеграции (сделано 2026-10-26)
- Согласие на БКИ даётся галочкой `form.consents.bki_request`, воркер не требует документ `bki_consent` (изменение в `worker/backend_protocol.py`).
- Базовая ставка берётся у продукта (`base_rate` в `worker/scoring.yaml`, как в каталоге и калькуляторе), а не у класса; тест `TestWorkerConfigMatchesTheCatalog` следит, чтобы ставки и списки документов не разошлись.
- API не подменяет настоящие данные демонстрационными: демо-режим включается только `DEMO_MODE=true` или пустым `DATABASE_URL`, при недоступных Postgres и Redis сервис не стартует.
- **Осталось:** тесты воркера (`worker/tests`) не запускаются в CI, а `.dockerignore` исключает их из образа; паспорт не считается подтверждённым (API не передаёт `verification_status`), поэтому без демо-образцов заявки идут на ручную проверку.

### 10. Действия клиента после решения — сделано
- `POST /applications/{id}/accept`: из `APPROVED` или `COUNTER_OFFER` кредит сразу выдаётся (`SIGNING → SIGNED → DISBURSED → ACTIVE`, подписание и выдача имитируются), записываются ставка, номер договора и дата выдачи. `POST /applications/{id}/decline`: `COUNTER_OFFER → DRAFT`.
- **Не сделано:** `REJECTED → DRAFT` («подать заново»), закрытие кредита (`ACTIVE → CLOSED`) и внесение платежей: `paid_payments` меняется только в демо-данных.
### 11. Рабочее место сотрудника — сделано (backend)
- `GET /employee/applications` — общий пул (`MANUAL_REVIEW`, никем не взятые, старые первыми), `?mine=true` — взятые мной; `GET /employee/applications/{id}` — карточка с документами, данными компании и ФИО взявшего; скачивание документов.
- «Взять в работу» (`take`) закрепляет заявку за сотрудником (`assigned_to`, `assigned_at`), она пропадает из пула; отдельного статуса нет. При одновременном нажатии получает один, второму 409 с ФИО. «Вернуть в очередь» (`release`). Через 2 часа без решения заявка сама возвращается в пул (фоновая задача раз в минуту).
- Решение (`decision`) только у взявшего: согласовать, отказать (причина обязательна), запросить документы (`MANUAL_REVIEW → INFO_REQUESTED`, после ответа клиента заявка снова в пуле), встречное предложение (сумма, срок, ставка вводит сотрудник; продукт по умолчанию тот же, другой — только если для него хватает полей и документов и он доступен компании).
- **Не сделано:** фронтенд рабочего места.

### 28. Сборщик для заявок, зависших в `DATA_CHECK` и `SCORING`
- **Суть:** сборщик повторно отправляет только заявки в `SUBMITTED`. Если воркер прислал `DATA_CHECK`, а потом упал или завис на внешнем сервисе, заявку никто не подберёт, и клиент будет видеть «проверка данных» бесконечно.
- **Что сделать:** расширить выборку сборщика на `DATA_CHECK` и `SCORING` с отдельным, более длинным порогом (например, 15 минут: разбор PDF и запросы в БКИ идут дольше двух минут). Воркер получит задачу повторно; первым сообщением он пришлёт `SUBMITTED → DATA_CHECK`, которое API отклонит как устаревшее, это нормально.
- **Где:** [repository/application.go](../internal/repository/application.go) (`ClaimStaleSubmitted`), [service/sweeper.go](../internal/service/sweeper.go).

## Слабые места в коде

Найдены при разборе backend 2026-10-24. «Подтверждено» означает, что проблема воспроизведена на запущенном стеке; остальное следует из чтения кода.

### Серьёзные

#### 15. `submit` может отправить заявку, не прошедшую проверку
- **Суть:** `Submit` читает заявку, проверяет поля и допуск продукта, а затем выполняет `UPDATE ... WHERE status = 'DRAFT'` без условия по `version`. Если между чтением и `UPDATE` пройдёт `PATCH` (вторая вкладка, автосохранение), отправится уже изменённая заявка: например, с пустой целью или с продуктом, недоступным компании.
- **Что сделать:** передавать в `UPDATE` версию, которую проверяли (`AND version = $v`); при несовпадении 409. Контракт для фронта не меняется.
- **Где:** [service/application.go](../internal/service/application.go) (`Submit`), [repository/application.go](../internal/repository/application.go) (`Submit`).

#### 16. Лимит неверных паролей обходится параллельными запросами (подтверждено)
- **Суть:** счётчик неудач сначала читается, затем идёт проверка bcrypt (около 60 мс), и только потом счётчик увеличивается. 20 одновременных запросов с неверным паролем дали 6 проверок пароля вместо 3; чем больше параллельных запросов, тем больше попыток.
- **Что сделать:** сначала увеличивать счётчик (`INCR`) и решать по его значению, при успешном входе сбрасывать.
- **Где:** [service/auth.go](../internal/service/auth.go) (`Login`), [repository/auth_store.go](../internal/repository/auth_store.go).

#### 17. Некорректный результат воркера повторяется бесконечно (подтверждено)
- **Суть:** `decision` вида `{"note":"a\u0000b"}` корректен для Go, но Postgres его не принимает (`SQLSTATE 22P05`). API считает это временным сбоем и повторяет обработку каждые 30 секунд без конца; заявка не меняется, журнал засоряется. То же с нулевым байтом в `comment`.
- **Что сделать:** ошибки данных Postgres (классы `22` и `23`) считать окончательными и подтверждать сообщение; для остальных ошибок ограничить число повторов.
- **Где:** [service/results.go](../internal/service/results.go), [queue/results.go](../internal/queue/results.go).

### Средние

#### 18. Содержимое формы не проверяется по типам
- **Суть:** при отправке проверяется только, что обязательное поле не пустое. В денежное поле можно передать строку, в `select` значение не из списка, в форму лишние группы. Воркер скоринга получит эти данные в задаче.
- **Что сделать:** при `submit` (а лучше и при сохранении) проверять значения по `type` и `options` из каталога.
- **Где:** [catalog/catalog.go](../internal/catalog/catalog.go) (`MissingFormFields`, `filled`).

#### 19. Лимит кодов 2FA при настоящем OTP
- **Суть:** зная пароль, можно запрашивать новые коды без ограничения и каждый раз получать ещё 3 попытки. Параллельные проверки одного кода теоретически обходят счётчик (в проверке на стеке лимит удержался). Пока работает заглушка, это не критично.
- **Что сделать:** при подключении настоящего OTP ограничить число вызовов на пользователя и учитывать попытку до проверки кода.
- **Где:** [service/auth.go](../internal/service/auth.go) (`Verify`).

#### 20. У HTTP-сервера нет таймаутов
- **Суть:** задан только `ReadHeaderTimeout`; медленно передаваемое тело запроса держит соединение сколько угодно.
- **Что сделать:** задать `ReadTimeout`, `WriteTimeout` и `IdleTimeout` (с учётом того, что `/me/bootstrap` ждёт воркера до 8 секунд).
- **Где:** [app/app.go](../internal/app/app.go).

#### 21. Сессию нельзя отозвать
- **Суть:** нет выхода (`logout`); отключённый пользователь (`is_active = false`) остаётся в системе до 8 часов; токены хранятся в Redis открытым текстом в имени ключа.
- **Что сделать:** метод выхода, проверка `is_active` (или удаление сессий при отключении), хранить хэш токена.

#### 22. Ключ идемпотентности может не защитить от повтора
- **Суть:** если сохранение ответа (`Finish`) не удалось, ошибка только пишется в журнал; через минуту ключ освобождается, и повтор с тем же ключом выполнится заново (например, создаст второй черновик). То же, если обработчик работает дольше 60 секунд.
- **Что сделать:** при ошибке `Finish` повторять запись или продлевать «в работе»; срок «в работе» согласовать с длительностью обработчиков.
- **Где:** [middleware/idempotency.go](../internal/middleware/idempotency.go), [repository/idempotency.go](../internal/repository/idempotency.go).

### Низкие

#### 23. `INCR` и `EXPIRE` выполняются отдельными командами
- Если процесс упадёт между ними, счётчик неудач останется без срока жизни, и вход будет заблокирован навсегда. Выполнять обе команды одним pipeline. [repository/auth_store.go](../internal/repository/auth_store.go) (`incr`).

#### 24. Статический сервер показывает список файлов (подтверждено)
- `GET /assets/` отдаёт перечень файлов каталога. Отключить листинг. Заодно: страницы `/employee`, куда перенаправляется сотрудник после входа, в `web/` нет (404).

#### 25. `/healthz` не проверяет базу и Redis
- Docker считает приложение здоровым, даже когда база недоступна. Добавить проверку зависимостей (или отдельный `/readyz`).

#### 26. Сборщик повторяет отправку без ограничения
- Пока воркер скоринга выключен, каждая заявка в `SUBMITTED` уходит в очередь раз в 2–3 минуты, копии накапливаются. Ограничить число повторов или хотя бы выводить их число в журнал. [service/sweeper.go](../internal/service/sweeper.go).

#### 27. Неизвестные поля JSON молча игнорируются
- Опечатка в имени поля (`termMonths` вместо `term_months`) не даёт ошибки, значение просто не сохраняется. Рассмотреть `DisallowUnknownFields` в [handler/response.go](../internal/handler/response.go).

## Улучшения без срока

- **Ошибки воркера кредитной истории.** Сейчас любое поле `error` считается временной недоступностью. Чтобы отличать «неизвестный ИНН», нужен код ошибки в ответе воркера ([worker-protocol.md](worker-protocol.md), «Открытые вопросы»).
- **Redis без авторизации и TLS.** Для демо допустимо; для боевого использования включить пароль и TLS.
- **Обрезка `applications:results`.** Подтверждённые записи остаются в журнале; добавить `XTRIM` или `MAXLEN` при росте.
- **Демо-данные.** Миграцию `00002_seed_demo_data.sql` убрать из боевой базы.
