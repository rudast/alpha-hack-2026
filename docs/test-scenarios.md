Сценарии 1–2 и группы A, B, C, D реализованы и проверены на запущенном стеке, остальные описывают целевое поведение. Тестовые учётные записи перечислены в [README](../README.md#тестовые-учётные-записи).

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Вход клиента по телефону или по почте и паролю, затем код 2FA | Токен и `redirect: /personalAccount` |

| 6 | Переход к заявке со страницы входа | ИНН и тип организации вводятся вручную |
| 7 | Отправка заявки с пустыми обязательными полями | Отправка блокируется, фокус на первом пустом поле |
| 8 | Заявка без подписанных согласий на БКИ | Отправка блокируется |
| 9 | Полная заявка, хороший скоринг | `SUBMITTED → DATA_CHECK → SCORING → APPROVED`, статусы видны клиенту |
| 10 | Заявка с недостающими данными | `INFO_REQUESTED`, клиент отвечает внутри заявки |
| 11 | Сложный случай или негативный скоринг | `MANUAL_REVIEW`, решение принимает андеррайтер |
| 12 | Встречное предложение | Клиент может принять, изменить параметры или подать заново |
| 13 | Отказ (выносит сотрудник) | Показаны причина и альтернативные продукты (меньшая сумма, больше залога) |

## Заявки клиента (черновик, просмотр, отправка)

Реализовано и проверено в `scripts/smoke.sh`. При отправке задача воркеру скоринга уходит сразу (группа C ниже); пока воркера скоринга нет, заявка остаётся в `SUBMITTED`.

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| B1 | Первое сохранение формы: `POST /applications` | 201, статус `DRAFT`, компания и автор взяты из сессии |
| B2 | Создание с неизвестным продуктом или отрицательной суммой | 400 |
| B3 | Автосохранение: `PATCH /applications/{id}` с актуальной `version` | 200, изменены только переданные поля, `form` заменена целиком, версия выросла на 1 |
| B4 | Список заявок | 200, только заявки своей компании, от новых к старым |
| B5 | Чужая заявка: просмотр, изменение, отправка; некорректный id в адресе | 404 во всех случаях (чужая неотличима от несуществующей) |
| B6 | Отправка неполной заявки | 422 `{"missing_fields": [...]}`, поля формы вида `группа.поле` |
| B7 | Отправка полной заявки | 200, статус `SUBMITTED`, в `history` запись `DRAFT → SUBMITTED` |
| B8 | Повторная отправка и изменение после отправки | 409 |
| B9 | Продукт недоступен компании (продукт только для ООО, компания ИП) или срок вне диапазона | 422 `{"error": ...}` |
| B10 | Методы заявок без токена или токеном сотрудника | 401, 403 |
| B11 | `PATCH` по устаревшей `version` (заявку уже изменила другая вкладка) | 409, чужие изменения не затёрты |
| B12 | `PATCH` без `version` | 400 |
| B13 | Десять одновременных `PATCH` с одной версией и разными ключами | один 200, остальные 409, версия выросла ровно на 1 |
| B14 | `POST`/`PATCH` по заявкам без `Idempotency-Key` | 400 |
| B15 | Повтор создания, сохранения или отправки с тем же ключом и тем же телом | тот же ответ, действие не выполнено второй раз (второго черновика нет, версия не выросла) |
| B16 | Тот же ключ для другого запроса | 422 |
| B17 | Десять одновременных созданий с одним ключом | создан ровно один черновик, все ответы про него |
| B18 | Новая отправка уже отправленной заявки с новым ключом | 409 |

## Предварительное предложение

Реализовано и проверено на запущенном стеке (подробно: [preapproved-offer.md](preapproved-offer.md)). Пока у компаний нет истории БКИ, лимит не выше 1 млн ₽.

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| E1 | Клиент `+79990000001` (капитал 5 млн, долг 3 млн) вызывает `GET /me/offer` дважды | Оборотный кредит до 1 000 000 ₽, 12 мес, ставка от 17,5 %, действует 30 дней; второй раз то же предложение (тот же `id`) |
| E2 | Клиент `+79990000004` (D/E 3,5) | `offer: null`, `reason: high_debt_load` |
| E3 | Клиент `+79990000002` до и после `/me/bootstrap` | До: `reason: no_data`; после: предложение |
| E4 | `POST /applications { offer_id }` с чужими `product_id` и `amount` в теле | 201, продукт, сумма и срок из предложения, в заявке `offer_id` |
| E5 | Повторное «Оформить» с тем же `offer_id` | 200, тот же черновик |
| E6 | `offer_id` другой компании | 404 |
| E7 | `PATCH` с суммой больше лимита | 422, `reason: offer_amount_exceeded`; меньше лимита — 200 |
| E8 | Смена продукта в заявке по предложению | Предложение отвязано (`offer_id: null`), заявка обычная (проверено юнит-тестом) |
| E9 | Отправка заявки по предложению | 200, предложение становится `USED`; следующий `GET /me/offer` считает новое |
| E10 | Заявка по использованному предложению | 409 |
| E11 | Предложение истекло, пока заполнялась форма | При отправке 422, `reason: offer_expired` (проверено юнит-тестом) |

## Сборщик застрявших заявок

Реализовано и проверено вручную на запущенном стеке (порог 2 минуты, поэтому проверка занимает около 7 минут). Задача уходит в stream `applications:submitted`.

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| C1 | Клиент отправляет заявку (`POST /applications/{id}/submit`) | Ответ 200; сразу в очереди одно сообщение с данными заявки и показателями компании, у заявки заполнен `enqueued_at`, версия не изменилась |
| C2 | Статус заявки сменился (воркер приступил к работе) | В очередь она не попадает, `enqueued_at` пуст |
| C3 | Заявка по-прежнему в `SUBMITTED` через минуту после первой отправки | Повторной отправки нет (не чаще раза в 2 минуты) |
| C4 | Заявка по-прежнему в `SUBMITTED` через 2–3 минуты после первой отправки | Задача отправлена повторно (второе сообщение) |
| C5 | Сбой отправки по одной заявке | Остальные обрабатываются, эта будет взята снова после порога |
| C6 | Задачу не удалось отправить в момент `submit` (недоступна очередь) или не поставилась метка `enqueued_at` | Клиент получает 200, заявка в `SUBMITTED`; ошибка в логе; задачу позже отправит сборщик (сбой метки проверен вручную на базе без колонки `enqueued_at`: 200 и ошибка в логе; сбой отправки в очередь проверен юнит-тестом, вручную не воспроизводился, потому что без Redis не работают вход и идемпотентность) |

## Приём результатов воркера скоринга

Реализовано и проверено вручную на запущенном стеке: результаты кладутся командой `XADD applications:results ...` (см. [worker-protocol.md](worker-protocol.md#результаты-воркера-скоринга-черновик-не-согласован)).

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| D1 | `SUBMITTED → DATA_CHECK` для отправленной заявки | Статус `DATA_CHECK`, версия +1, в истории запись с `by: worker` |
| D2 | Тот же результат пришёл повторно | Заявка не меняется (версия и история прежние), сообщение подтверждено |
| D3 | `DATA_CHECK → SCORING → APPROVED` с `decision` | Статус `APPROVED`, решение сохранено в `decision` как прислано, в истории три перехода воркера |
| D4 | Воркер прислал `to = REJECTED` | Отклонено, заявка не меняется, причина в журнале |
| D5 | Переход не по диаграмме (например, `SUBMITTED → SCORING`) | Отклонено, заявка не меняется |
| D6 | Устаревший `from` (заявка в другом статусе) | Пропущено, заявка не меняется |
| D7 | Заявки не существует или `application_id` не UUID | Пропущено, сообщение подтверждено |
| D8 | В сообщении нет поля `to`; `decision` не JSON-объект | Отброшено, подтверждено |
| D9 | После всех сообщений | В группе `api` нет «зависших» (`XPENDING` равно 0) |
| D10 | База недоступна в момент прихода результата | Сообщение не подтверждается; после возвращения базы применяется само через 30–40 секунд |
| D11 | Три воркера кредитной истории (`docker compose up --scale worker=3`) | Все три в одной группе, 12 запросов обработаны, зависших нет |
| D12 | Воркер прислал `MANUAL_REVIEW → APPROVED` (решение вместо сотрудника) | Отклонено, заявка остаётся в `MANUAL_REVIEW`, причина в журнале |
