Состояние на 25.10.2026, ветка `main`.

## Принятые решения

1. **Кредит — это заявка.** Отдельной таблицы кредитов нет. Одна строка `applications` проходит весь путь, этап определяется статусом:

   | Статус | Для клиента | Где в кабинете |
   |---|---|---|
   | `DRAFT` | черновик | «Мои заявки» |
   | `SUBMITTED`, `DATA_CHECK`, `SCORING`, `MANUAL_REVIEW` | на рассмотрении | «Мои заявки» |
   | `APPROVED`, `COUNTER_OFFER` | банк одобрил, ждём ответа клиента | «Мои заявки», кнопки «Принять» / «Отказаться» |
   | `ACTIVE`, `OVERDUE` | действующий кредит | «Мои кредиты» |
   | `CLOSED` | закрытый кредит | «Кредитная история» |

   `GET /applications` отдаёт всё до выдачи, `GET /loans` — `ACTIVE`, `OVERDUE` и `CLOSED`.
2. **График платежей не храним**, а считаем на лету из суммы, ставки, срока, даты выдачи и числа внесённых платежей.
3. **Одобрение подтверждает клиент.** Скоринг выставил `APPROVED` → клиент нажимает «Подписать и получить» → кредит сразу становится `ACTIVE`.
4. **Встречное предложение** клиент принимает (кредит на новых условиях сразу становится `ACTIVE`) или отклоняет (заявка возвращается в `DRAFT`).
5. **Каталог продуктов: правильные значения — как в калькуляторе** (`web/assets/js/loans.js`). Бэкенд переносит их в `products.yaml`.
6. **Кредиты в других банках** берутся из `companies.credit_history`, в сиде — списком.
7. **Спорные заявки решает сотрудник банка.** Скоринг одобряет хорошие заявки сам (`APPROVED`), остальные отправляет на ручную проверку (`MANUAL_REVIEW`). Сотрудник открывает заявку (она закрепляется за ним) и одобряет, отклоняет с причиной, предлагает другие условия (сумма, срок, вид кредита), запрашивает документы или откладывает. Клиент видит всё, кроме «отложить». Подробно — задача 9.

## Общие правила для всех методов

- Деньги — целые рубли, число: `1500000`. Ставка — проценты годовых, число: `19.5`.
- Дата без времени — `"2026-11-15"`. Момент времени — RFC 3339: `"2026-10-24T15:31:00Z"`.
- Ошибка — `{"error": "..."}` и правильный HTTP-статус: без токена 401, не клиент 403, чужая или несуществующая запись 404.
- Компания берётся из сессии (`CompanyINN`), не из запроса.
- Все изменяющие запросы — через `Idempotency-Key`, как уже сделано для заявок.
- Поле без данных присутствует в ответе со значением `null` или `[]`.
- Новые колонки — **новой миграцией**, а не правкой `00001_init.sql`: у кого база уже создана, правка старой миграции не применится. В ветке `parsing` уже есть `00003` и `00004`, номер согласовать при слиянии.

## Задача 2. Кредит в таблице заявок

### 2.1. Миграция: поля выданного кредита в `applications`

| Колонка | Тип | Смысл |
|---|---|---|
| `rate` | `numeric(5,2)` | ставка выданного кредита, % годовых |
| `contract_number` | `text` | номер договора, например `0ОС-2026/1187` |
| `issued_at` | `date` | дата выдачи; день месяца = день платежа |
| `paid_payments` | `integer NOT NULL DEFAULT 0` | сколько ежемесячных платежей внесено |
| `closed_at` | `date` | дата закрытия (для `CLOSED`) |
| `late_payments` | `integer NOT NULL DEFAULT 0` | сколько платежей было внесено с опозданием (для истории) |

`amount` и `term_months` уже есть: у выданного кредита это одобренные сумма и срок.

### 2.2. Как считать график

Аннуитет, как в `buildLoan` в `mock-api.js`:

- `r = rate / 100 / 12`, платёж `P = amount · r / (1 − (1 + r)^−term_months)`, округлить до копеек;
- платёж № n: дата `issued_at + n месяцев` (31-е в коротком месяце → последний день месяца), проценты `= остаток · r`, основной долг `= P − проценты`, последний платёж закрывает остаток целиком;
- статус платежа:
  - `n ≤ paid_payments` → `PAID`;
  - `n = paid_payments + 1` → `OVERDUE`, если его дата уже прошла, иначе `NEXT`;
  - остальные → `PLANNED`.
- Если есть просроченный платёж, статус кредита `OVERDUE`, иначе `ACTIVE`.
- Досрочно закрытый кредит (`CLOSED`, платежей меньше, чем `term_months`): последний платёж № `paid_payments` гасит весь остаток.

### 2.3. Как заявка становится кредитом

| Событие | Переход | Что записать |
|---|---|---|
| Клиент принимает одобрение (задача 4) | `APPROVED` → `SIGNING` → `SIGNED` → `DISBURSED` → `ACTIVE` | `rate` (из `decision`: `offer.rate`, иначе ставка решения, иначе ставка продукта из каталога), `contract_number` (сгенерировать), `issued_at = сегодня`, `paid_payments = 0` |
| Клиент принимает встречное предложение | `COUNTER_OFFER` → … → `ACTIVE` | то же, но `amount`, `term_months`, `rate` взять из `decision.offer` |
| Закрытие кредита | `ACTIVE` → `CLOSED` | `closed_at`. Для демо закрытие делать не нужно, закрытые кредиты есть в сиде |

Все промежуточные переходы пишутся в `history`, как сейчас.

## Задача 4. Ответ клиента на решение банка

Клиент, роль `client`, с `Idempotency-Key`. Скоринг уже выставляет `APPROVED` и `COUNTER_OFFER` через воркер, диаграмма переходов в `domain/application.go` их разрешает.

| Метод | Из статуса | Результат |
|---|---|---|
| `POST /api/v1/applications/{id}/accept` | `APPROVED` или `COUNTER_OFFER` | заявка становится кредитом `ACTIVE` (см. 2.3); ответ — заявка целиком, как `GET /applications/{id}` |
| `POST /api/v1/applications/{id}/decline` | `COUNTER_OFFER` | `DRAFT`; клиент может поменять условия и подать заново |

| `POST /api/v1/applications/{id}/resubmit` | `INFO_REQUESTED` | клиент дослал запрошенные документы: `INFO_REQUESTED` → `DATA_CHECK` → `MANUAL_REVIEW`, заявка возвращается к тому же сотруднику и встаёт наверх его очереди. Если приложены не все запрошенные документы — `422 {"missing_documents": ["…"]}` |

Из другого статуса — `409 {"error": "application is not awaiting client decision"}`.

**Что кабинет клиента читает из заявки** (`GET /applications/{id}`):

| Поле | Зачем |
|---|---|
| `decision.offer` | `{ product_id, amount, term_months, rate }` — одобренные или предложенные условия |
| `decision.comment` | комментарий сотрудника к решению; при отказе — причина |
| `decision.requested_documents`, `decision.request_comment` | какие документы запросил сотрудник и пояснение |
| `assigned_to.full_name` | «Заявку рассматривает специалист банка Сидорова Анна Сергеевна» |
| `documents` | приложенные документы: `{ id, kind, filename, status, created_at }` |
| `history[]` | события с полями из задачи 9.3 |

В элементы `GET /applications` добавить `decision` (`outcome`, `offer`), `requested_documents` и `assigned_to.full_name`: по ним в карточке появляются кнопки «Подписать и получить», «Посмотреть условия», «Загрузить документы».

## Задача 6. Загрузка документов к заявке

В ветке `parsing` есть таблица `application_documents` и разбор документов воркером, но метода загрузки для клиента нет ни там, ни в `main`.

`POST /api/v1/applications/{id}/documents` — клиент, `Idempotency-Key`, пока заявка `DRAFT` или `INFO_REQUESTED` (банк запросил документы).

- Запрос `multipart/form-data`: `kind` (вид документа из каталога: `passport`, `account_statement`…) и `file` (PDF, JPG, PNG, до 10 МБ).
- Ответ 201: `{ "id": "…", "kind": "passport", "filename": "pasport.pdf", "status": "UPLOADED", "created_at": "…" }`.
- Список документов — в поле `documents` ответа `GET /applications/{id}`.
- `DELETE /api/v1/applications/{id}/documents/{docId}` — пока заявка `DRAFT`.

Согласия на запрос в БКИ и обработку данных фронт кладёт в `form.consents`: `{ "bki_request": true, "personal_data": true }`. При `submit` стоит проверять, что `bki_request = true`.

## Задача 7. Демо-данные в сиде

Кабинет сейчас показывает эти кредиты из заглушки. После переключения он должен выглядеть так же.

Даты действующих кредитов считаются от дня запуска, как в `anchorDate` в `mock-api.js`:

1. Ближайшая дата платежа `D` — ближайшее число `pay_day`, которое сегодня или позже. Пример на 25.10.2026 при `pay_day = 15`: `D = 2026-11-15`.
2. `issued_at = D − (paid_payments + 1) месяцев`. Для примера при 7 внесённых: `2026-03-15`. Тогда платежи № 1–7 уже прошли, № 8 — ближайший.
3. Для просроченного кредита `D` — последнее число `pay_day`, которое было **не позже чем 5 дней назад**. Пример на 25.10.2026 при `pay_day = 10`: `D = 2026-10-10`, `issued_at = 2026-04-10`, платёж № 6 просрочен.

Проще всего считать это в Go при запуске сида или пересчитывать даты демо-кредитов при старте приложения; в SQL-сиде даты устареют через месяц.

## Как проверить

```bash
# вход демо-клиентом (пароль у всех demo-password, код 000000)
CH=$(curl -s -X POST localhost:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"role":"client","login":"+79990000001","password":"demo-password"}' | jq -r .challenge_id)
TOKEN=$(curl -s -X POST localhost:8080/api/v1/auth/verify -H 'Content-Type: application/json' \
  -d "{\"challenge_id\":\"$CH\",\"code\":\"000000\"}" | jq -r .token)

curl -s localhost:8080/api/v1/loans -H "Authorization: Bearer $TOKEN" | jq
curl -s localhost:8080/api/v1/products | jq '.products | length'   # 14
```

Демо-клиенты: `+79990000001` (Торг) … `+79990000005` (ИП Иванов).

Метод готов, когда:

- ответ совпадает по полям и типам с примером из этого файла;
- для всех пяти демо-клиентов цифры совпадают с таблицами задачи 7;
- без токена 401, сотрудник 403, чужая запись 404;
- метод описан в `docs/openapi.yaml` и `docs/requests.http`;
- влито в `main`, `docker compose up --build` поднимается на чистой базе (`docker compose down -v`).

## Как будем интегрировать

Кабинет ходит на сервер через общую функцию `api()`. Заглушка в `mock-api.js` подменяет ответ только для методов из списка `MOCKS`; экраны не знают, откуда пришли данные. Поэтому методы подключаются по одному:

1. Бэкенд вливает метод в `main` и пишет во фронт-чат.
2. Фронт ставит `false` нужному методу в `MOCKS`:
   ```js
   var MOCKS = {
     'GET /me': false,      // готово на бэкенде
     'GET /loans': true,
     'GET /me/offer': true,
   };
   ```
   Значок «демо-данные» у блока пропадает сам.
3. Проходим пятерых демо-клиентов и сверяем экраны со скриншотами до переключения.

Что фронт доделывает после бэкенда:

| После задачи | Фронт |
|---|---|
| 3 | выключает заглушку `GET /loans` |
| 4 и 9 | убирает `mock-review.js`; окно заявки у клиента и кабинет сотрудника уже готовы. Добавить автообновление статуса заявки, пока она на проверке |
| 5 | калькулятор и мастер грузят каталог из `GET /products`, копии в `loans.js` и `catalog.js` и соответствие id калькулятора и бэкенда (`working-capital` → `working_capital`) удаляются |
| 6 | шаг «Документы» отправляет файлы |

Рассмотрение заявок (задачи 4, 6, 9) подменяет `mock-review.js`: он хранит демо-заявки в браузере, чтобы кабинет сотрудника и кабинет клиента в двух вкладках видели одно и то же. Когда методы задач 4 и 9 готовы, подключение `mock-review.js` удаляется со страниц `/personalAccount/` и `/employee/` — экраны уже вызывают нужные методы.

Когда все методы готовы, подключение `mock-api.js` удаляется со страниц.

Порядок, в котором удобнее всего: **1 → 2 → 3 → 7** (кабинет показывает настоящие кредиты), затем **4 + 9** (рассмотрение заявок), **5**, **6**.
