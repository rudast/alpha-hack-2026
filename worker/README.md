# Python worker

Отдельный сервис обработки задач Go API. В Docker Compose по умолчанию используется `WORKER_PROTOCOL=backend`. Режим `legacy` использует Redis Stream `worker:requests`: маршрутизатор в `router.py` переносит задачи в `worker:fast` или `worker:slow`. Контракт этого режима описан в [worker-tasks.md](../docs/worker-tasks.md).

`WORKER_PROTOCOL=backend` включает контракт ветки `origin/backend`. В нём восемь быстрых потребителей читают `credit-history:requests` и `applications:submitted`; два медленных потребителя читают `worker:backend:slow`. Ответ БКИ идёт в список `credit-history:reply:<request_id>`, а изменения статуса заявки — отдельными полями `event_id`, `application_id`, `from`, `to`, `decision`, `info_request`, `comment` в `applications:results`. Перед следующим переходом worker ждёт подтверждения предыдущего события группой API `api`; при отсутствии подтверждения задача остаётся в Redis для повтора. Оба режима работают без доступа к PostgreSQL.

Исходное сообщение `applications:submitted` остаётся в pending до публикации итогового результата. Внутренняя очередь `worker:backend:slow` и отметка `worker:backend:routed` позволяют восстановить обработку после остановки быстрого или медленного потребителя без повторной маршрутизации той же Redis-задачи. Медленный потребитель продлевает владение задачей каждые 20 секунд; после остановки другой экземпляр забирает её через `XAUTOCLAIM` с порогом 60 секунд. После итогового результата оба подтверждения и удаление отметки выполняются одной Redis-транзакцией.

Режимы запускаются по отдельности: два варианта API используют разные форматы сообщений в одном `applications:results`. Старые задания `worker:requests` режим `backend` не читает.

| Модуль | Класс | Задачи |
|---|---|---|
| `services/financial_verifier.py` | быстрый | `credit_history`, `verify_application` |
| `services/document_parser.py` | длительный | `parse_documents` — CSV-выписки и универсальные CSV-отчёты маркетплейса, частично выписки 1С и учебные JSON-отчёты; текст PDF/DOC/DOCX и OCR сканов |
| `services/document_readers.py` | длительный | Ограниченное по объёму извлечение текста из PDF, Word и изображений |
| `services/risk_reviewer.py` | длительный | `critical_risk_review` — заглушка |
| `scoring_engine.py`, `scoring.yaml` | длительный | Версионируемый расчёт факторов, балла, ставки и встречного предложения для 14 продуктов |

Для запуска отдельно от Compose нужны Redis, Python 3.13, `antiword`, `tesseract-ocr` и языковые пакеты `eng`, `rus`. PostgreSQL доступен только Go API:

```bash
python3 -m venv .venv
.venv/bin/pip install -r worker/requirements.txt
WORKER_PROTOCOL=backend REDIS_ADDR=localhost:6379 .venv/bin/python -m worker.main
```

Для прежнего протокола: `WORKER_PROTOCOL=legacy REDIS_ADDR=localhost:6379 .venv/bin/python -m worker.main`.

Для сквозного запуска с актуальным Go API нужно объединить `parsing` с `main` (или `backend`): в этих ветках пока нет Python воркера. После сборки Compose `POST /api/v1/me/bootstrap` даёт демо-компании долг и капитал; без этих показателей скоринг возвращает `INFO_REQUESTED`. Пример создания заявки и загрузки документов есть в `docs/requests.http`. Загруженные файлы проходят через общий том к Python воркеру. При отсутствии паспорта или согласия ответ — `INFO_REQUESTED`; непроверенные загруженные документы ведут к `MANUAL_REVIEW`.

### Демонстрация автоодобрения

Для пяти синтетических компаний можно включить проверяемые образцы паспорта и согласия. Ключ задаёт оператор демо; в репозитории его нет. Он должен быть одинаковым у генератора образцов и контейнера worker. Подпись привязывает каждый PNG к виду документа, заявке, ИНН, руководителю, цели запроса БКИ, получателю отчёта и дате. Данные сверяются со снимком заявки, согласие должно быть явно отмечено в форме. Изменённый или просроченный образец идёт на ручную проверку. Обычный PNG/PDF этим способом не подтверждается.

```bash
export WORKER_DEMO_ATTESTATION_KEY="$(openssl rand -hex 32)"
docker compose up -d --build
# Войдите демо-клиентом, вызовите POST /api/v1/me/bootstrap и создайте черновик.
demo_files_dir="$(mktemp -d /tmp/credit-demo-files.XXXXXX)"
.venv/bin/python -m worker.demo_fixtures \
  --application-id '<id черновика>' --inn 7700000002 \
  --subject-name 'Смирнова Ольга Ивановна' \
  --output-dir "$demo_files_dir"
# Загрузите оба PNG как passport и bki_consent через API, заполните форму и отправьте заявку.
```

Для `express` с 500 000 ₽ на 6 месяцев и демо-компанией `7700000002` сквозной тест получил `SUBMITTED → DATA_CHECK → SCORING → APPROVED`, балл 88,3 и ставку 24,76%. Решение помечается `evidence_mode: synthetic_demo`: это проверка конвейера, а не решение для реального клиента. Для обычных документов текущему API нужен доверенный результат проверки личности и согласия; входной контракт уже поддерживает `id`, `verification_status=VERIFIED` и `subject_inn`, но API пока их не передаёт.

Backend передаёт в `applications:submitted` снимок формы и список `documents` с `kind`, `name`, `path`. Worker сверяет комплект документов с `scoring.yaml`: базовые паспорт и согласие на БКИ плюс документы продукта из каталога. Недостающее запрашивается через `INFO_REQUESTED`; понятный текст дублируется в `comment`, так как backend пока не сохраняет `info_request`. При полном наборе данных worker считает балл по `scoring.yaml` и возвращает `APPROVED`, `COUNTER_OFFER` либо `MANUAL_REVIEW`. Для документа без `id` worker вычисляет стабильный идентификатор источника из заявки и пути; это идентификатор для трассировки, а не доказательство проверки. Непроверенные документы и признаки блокируют автоодобрение. Согласие на БКИ считается подтверждённым только при `verification_status=VERIFIED` и совпадении `subject_inn` с ИНН заявителя либо через подписанный демо-образец. `event_id` — стабильный UUID, построенный из заявки, идентификатора входного Redis-сообщения и перехода: повтор обработки того же сообщения сохраняет идентификатор, новая отправка получает новый. Нулевые символы из текстов результата удаляются перед отправкой.

Worker читает `documents[].path` относительно `WORKER_DOCUMENT_ROOT` или по абсолютному пути внутри этого каталога. Расширение определяет тип файла при отсутствии `media_type`. В Compose общий том `documents` подключён к API для записи и к Python worker только для чтения. Выход за пределы каталога, символьные ссылки и файлы больше 10 МиБ отклоняются. Этот Compose заработает с текущим API из `main` или `backend` после интеграции кода веток; в самой ветке `parsing` загрузки документов в API ещё нет.

Ограничения backend остаются за пределами worker: API из `main` и `backend` позволяет клиенту загрузить документ и повторно отправить заявку после `INFO_REQUESTED`, но не сохраняет отдельное поле `info_request` и не хранит `event_id` для отдельной проверки повторов. Ожидание подтверждения защищает порядок событий одной заявки при нескольких экземплярах API.

Пороговые значения и ставки в `scoring.yaml` демонстрационные. БКИ и реестры для пяти демо-компаний возвращают синтетические профили; частичный `credit_history` из демо-данных backend дополняется недостающими полями тестового профиля без замены полученных значений. Незнакомый ИНН не получает автоматически «чистую» историю. Запускать автоматические решения на реальных данных без проверки источников и утверждения правил нельзя. Тесты: `python -m unittest discover -s worker/tests`; интеграционные тесты Redis включаются переменной `REDIS_TEST_ADDR` на отдельной тестовой базе.

PDF с текстовым слоем читается через PDFium; для страниц без текста и загруженных изображений запускается OCR. DOCX читается как Word-документ, старый DOC преобразуется в текст через `antiword`. Результат помечается `TEXT_EXTRACTED` и требует проверки: из текста бухгалтерских форм извлекаются только явно помеченные строки 2110, 2400, 1300, 1400 и 1500 с единицей измерения и годом; из выписок ЕГРЮЛ/ЕГРИП и ЕГРН, ПТС/СТС и техпаспорта — идентификаторы; из отчёта об оценке и договоров — явно помеченные суммы. Все значения остаются непроверенными. Лимиты: 20 страниц, 12 млн пикселей на OCR-страницу, 30 тыс. символов результата. API принимает файл до 10 МиБ.

CSV-выписка поддерживает явные колонки `date,credit,debit,balance` или `Дата,Поступление,Списание,Остаток`, кодировки UTF-8/CP1251/CP866, копейки и прямой/обратный порядок строк. Остаток между соседними операциями сверяется, суммы сохраняются строками в рублях с копейками. Дополнительные колонки счёта и валюты проверяются; другие валюты и неизвестный состав колонок получают `UNSUPPORTED`. Универсальный CSV отчёта маркетплейса использует `period,sales,returns,payouts` или соответствующие русские заголовки и не выдаётся за выгрузку конкретной площадки. Те же таблицы извлекаются из PDF/Word/OCR, если при чтении сохранились границы столбцов; иначе остаётся текст для ручной проверки.

Выписки `1CClientBankExchange` в `text/plain` читаются из секций `СекцияРасчСчет`: обороты по месяцам, номер счёта и остатки. Пока поддерживается один счёт в файле; каждая секция должна лежать внутри одного календарного месяца, а секции вместе должны покрывать заявленный период. Файл без итогов секции получает `UNSUPPORTED`; расхождение баланса — `FAILED`. Произвольные макеты PDF-выписок банков и все варианты формата 1С пока не покрыты.

В режиме `legacy` Go API передаёт файлы в задачах Redis в base64. Worker отправляет результаты в `applications:results`; Go сохраняет их и отдаёт через `GET /api/v1/applications/{id}`.
